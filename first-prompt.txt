# Venice Forge Live Repository Audit — 2026-08-18

I audited live `main` at commit `49827d510b0c520d0002eb6e95f78e3f4e430f7d`, whose latest change updates `docs/summary_of_work.md`. The current package is `3.0.0-beta.2`.  

I used the uploaded remediation work order as the expected behavior contract, especially its non-negotiable Family Safe Mode, profile/master-password, media, Traffic Inspector, and browser requirements. 

One important scope note: this was a **live source audit through GitHub**, not a local checkout execution. The repository's latest work ledger records `test:ci` at 5,005 passing tests across 464 files, `verify:contracts` at 103/103, clean lint/typecheck, and a successful production build, but I could not independently retrieve the current Actions run state through the connector. 

## Executive verdict

The repo has advanced considerably. Most of the old Electron, ingestion, CI segmentation, image tooling, profile storage, media persistence, and Traffic Inspector work has landed.

It is **not release-ready against the supplied remediation contract**.

I found three P0-class blockers:

1. **Family Safe Mode can be bypassed at the main-process configuration boundary.** The master-password requirement is currently enforced primarily by renderer UI, while `config:writeSanitized` accepts a safety patch in main without master-password authorization.   
2. **Family Safe Mode does not authoritatively force Venice provider `safe_mode:true`.** Main deliberately treats the provider toggle as independent even when Family Safe Mode is ON. The existing regression test passes because provider Safe Mode defaults to true; it does not exercise `family=true/provider=false`.   
3. **Generated binary media is not semantically screened before display/persistence.** Current response screening replaces binary image/audio/video fields with `[binary-media]` before running a text classifier. That cannot detect an unsafe generated image. This directly leaves the response/display layer from the work order incomplete.  

Several P1 issues also remain: post-delta automatic stream replay, character context-file prompt injection, video cancellation semantics, character required-field enforcement, Research Browser removal versus the requested browser feature, and workflow output idempotency.

# 1. P0 findings

## P0-001 — Family Safe Mode password lock is renderer-mediated and bypassable at the main configuration boundary

This is the highest-confidence new finding.

The normal Settings flow looks correct at first glance. `SafetyPanel` opens `MasterPasswordDialog` before changing Family Safe Mode. The dialog either creates or verifies the password, and only on success does Settings call `onUpdateSafetySetting()`.  

But the authoritative write is then:

```ts
desktopConfig.writeSanitized({
  safety: {
    local_family_safe_mode_enabled: enabled
  }
})
```

`config:writeSanitized` in Electron main accepts the patch and calls `writeSanitizedConfig(patch)` with no master-password proof, capability token, or verification check. Its only wrapper is IPC rate limiting.  

That violates the work-order requirement that the renderer not be trusted for safety state and that a master password control Family Safe Mode changes. 

There is a second weakness in the same boundary. `masterPassword:set` simply calls `setMasterPassword(password)`; it does not reject an overwrite when a verifier already exists. `masterPassword:clear` deletes the master credential without requiring the current password. 

Meanwhile, `SafetyPanel` decides whether to run setup or verification from `useProfileStore().masterPasswordSet`, which is renderer-persisted metadata rather than an authoritative main-process `isMasterPasswordSet()` query.  

### Concrete failure path

A stale/reset/tampered renderer state can report:

```text
masterPasswordSet = false
```

The dialog enters `setup` mode and invokes:

```text
masterPassword:set
```

Main currently allows replacement of the existing verifier.

More directly, any renderer path able to invoke the exposed configuration bridge can submit the Family Safe Mode setting through `config:writeSanitized` without going through `MasterPasswordDialog` at all.

### Threat

Compromised renderer state, an unsafe future component, imported/corrupted state, or direct access to the exposed typed bridge can disable Family Safe Mode without proving knowledge of the master password.

### Affected surface

```text
src/components/settings/SafetyPanel.tsx
src/components/settings/MasterPasswordDialog.tsx
src/components/settings/SettingsView.tsx
src/stores/profile-store.ts
electron/ipc/configHandlers.ts
electron/ipc/handlers/apiKeyHandlers.ts
electron/services/secureStore.ts
```

### Required correction

Move the **entire authorization transaction into main**.

I recommend replacing the generic safety setting path with a typed operation such as:

```text
safety:setFamilySafeMode
```

Input:

```ts
{
  enabled: boolean
  masterPassword: string
}
```

Main must:

1. determine whether a master verifier exists;
2. validate password + lockout;
3. refuse the change on failure;
4. update YAML/runtime snapshot itself;
5. return the resulting authoritative safety snapshot;
6. never return/store the password.

Additionally:

- `config:writeSanitized` must reject patches containing `safety.local_family_safe_mode_enabled`.
- `masterPassword:set` must fail if a master password already exists.
- Add `masterPassword:change` requiring the existing password.
- `masterPassword:clear` must require current-password verification or an explicit destructive recovery procedure.
- Hydrate `masterPasswordSet` from `masterPassword:isSet`; renderer persistence must not be authoritative.

### Validation

```bash
npx vitest run \
  electron/ipc/configHandlers.test.ts \
  electron/ipc/handlers/apiKeyHandlers.test.ts \
  src/components/settings/SafetyPanel.test.tsx \
  src/components/settings/MasterPasswordDialog.test.tsx \
  --no-file-parallelism

npm run verify:safety-guard
npm run verify:contracts:static
```

Required negative tests:

```text
generic config write + family=false              => rejected
existing master + masterPassword:set(new)         => rejected
masterPassword:clear without current password     => rejected
incorrect password + safety toggle                => rejected
locked-out password + safety toggle               => rejected
correct password + safety toggle                  => accepted
```

Risk if ignored: the master-password protection is a UI convention rather than an authoritative security boundary.

## P0-002 — Family Safe Mode does not force provider `safe_mode:true`

The work order is explicit:

> Family Safe Mode ON must override provider `safe_mode` to `true`. 

The onboarding UI makes the same promise:

> “Family Safe Mode also forces provider safe_mode where supported.” 

Main currently does something else.

`withFamilySafeProviderOverride()` contains this explicit design comment:

```text
Family Safe Mode ... should NOT force it on without
the user explicitly opting in.
```

It reads only:

```ts
getRuntimeVeniceApiSafeMode()
```

and applies that value to the outbound body. 

So this state is possible at the authoritative dispatch boundary:

```text
Family Safe Mode = true
Venice API Safe Mode = false
```

Result:

```text
safe_mode = false
```

for an endpoint supporting provider Safe Mode.

The Settings UI prevents a normal click from producing that combination, but the main-process invariant is absent. Renderer/UI prevention is insufficient because the entire safety design correctly claims main is authoritative. 

### Why the current test misses it

The regression test named:

```text
forces provider safe_mode true for supported endpoints when Family Safe Mode is ON
```

sets Family Safe Mode ON but never explicitly sets provider Safe Mode OFF. `runtimeSafetySettings.ts` initializes the provider flag to `true`, so the test passes without proving the required override.  

This is a false-positive contract test.

### Correct invariant

For provider-supported endpoints:

```ts
effectiveSafeMode =
  getRuntimeLocalFamilySafeModeEnabled()
    ? true
    : getRuntimeVeniceApiSafeMode()
```

Or equivalently:

```ts
effectiveSafeMode =
  getRuntimeLocalFamilySafeModeEnabled() ||
  getRuntimeVeniceApiSafeMode()
```

Do this in the authoritative main/server dispatch layer, not just the renderer.

### Required test matrix

```text
Family ON  + Provider ON  => safe_mode true
Family ON  + Provider OFF => safe_mode true
Family OFF + Provider ON  => safe_mode true
Family OFF + Provider OFF => safe_mode false
unsupported endpoint      => no invented safe_mode field
```

Also validate imported YAML/config state:

```text
local_family_safe_mode_enabled: true
venice_api_safe_mode: false
```

must resolve outbound supported requests to:

```json
{"safe_mode": true}
```

### Validation

```bash
npx vitest run tests/safety/guardPipeline.test.ts --no-file-parallelism
npm run verify:safety-guard
npm run verify:image-policy
npm run verify:network-boundaries
```

Risk if ignored: the exact provider-side defense required to reduce unsafe image output can silently be disabled while the UI reports Family Safe Mode as ON.

## P0-003 — Generated binary image/media response screening is not implemented semantically

Main does run an upstream response screen. That part is good.

But before screening, `stringifyResponseForScreening()` deliberately replaces these keys:

```text
dataBase64
image
images
dataUrl
audio
video
```

with:

```text
[binary-media]
```

Then the rule engine screens only the remaining text/JSON representation. 

Therefore:

```text
provider returns unsafe generated PNG
        ↓
actual pixels are replaced with "[binary-media]"
        ↓
text classifier sees no visual content
        ↓
response can pass
```

`SECURITY.md` accurately admits this limitation: the local system does not inspect every binary/media payload semantically. 

That is defensible documentation, but it does **not** satisfy the supplied remediation contract, which requires response/display screening for the Family Safe Mode image bypass and says not to ship until it is fixed. 

### Required architecture

When Family Safe Mode is ON:

```text
request guard
→ forced provider safe_mode
→ provider dispatch
→ media decoding/validation
→ safety classification
→ persistence
→ display
```

Unsafe media must fail before both:

```text
generated media persistence
renderer display
```

This does not require live explicit-image tests. Use mocked classifier results and fixture-safe image buffers.

### Minimum contract

```ts
type GeneratedMediaSafetyResult =
  | { allowed: true }
  | {
      allowed: false
      reasonCode: string
      category: string
    }
```

The renderer must receive only the block result, never the rejected media.

### Validation

Add tests proving:

```text
safe synthetic image classifier result    => persisted/displayed
unsafe mocked classifier result            => not persisted
unsafe mocked classifier result            => no renderer media URL
classifier failure in Family Safe Mode     => fail closed
Family Safe Mode OFF                       => documented Adult Mode path
```

Then:

```bash
npm run verify:safety-guard
npm run verify:image-policy
npm run test:electron
npm run test:ui:media
```

Residual risk: semantic classifiers are imperfect, but the requested response/display safety layer would finally exist rather than being structurally incapable of inspecting pixels.

# 2. P1 findings

## P1-001 — Streaming still retries after observable partial output

This is the major open item from the August 15 exhaustive audit.

The current roadmap explicitly leaves WP-06 unresolved. 

`chat-stream-manager.ts` has automatic retries for retryable network/status failures. It buffers/flushes deltas to the conversation, but no durable state prevents another provider request after user-visible content/tool/appended-message output has already occurred. 

So a sequence can be:

```text
provider attempt #1
→ visible partial output
→ 5xx / network interruption
→ automatic retry
→ provider attempt #2
```

That can produce duplicate continuation, divergent text, duplicate tool effects, and multiple billable generations from one user action.

### Required fix

Introduce something equivalent to:

```ts
let observableOutputSeen = false
```

Set it before exposing any:

```text
content delta
reasoning delta
tool call
appended message
generated media
managed document
```

On retryable failure:

```ts
if (observableOutputSeen) {
  persistPartialResult()
  exposeExplicitRetryAction()
  return
}
```

Only zero-output transport failures may auto-retry.

### Validation

```bash
npx vitest run src/stores/chat-stream-manager.test.ts --no-file-parallelism
```

Required tests:

```text
failure before first delta → may retry
failure after content delta → provider called exactly once
failure after reasoning delta → provider called exactly once
failure after tool call → provider called exactly once
failure after appended message → provider called exactly once
partial output preserved
explicit user Retry creates a new request
```

## P1-002 — Character context files are elevated into system context as executable-looking instructions

Character file validation itself is substantially implemented. The editor limits context files to PDF/TXT/MD and 5 MiB and extracts PDF text. 

The problem is downstream prompt construction.

`buildCharactersBlock()` places creator instructions and general context-file text directly into the character block:

```text
[Creator instructions]
<content>

[Sourced Context Files]
[Sourced File: filename]
<raw content>
```

That character block is assembled into privileged RP prompt context. There is no robust inert-data encoding or delimiter escaping visible at this boundary. 

An uploaded `.txt`, `.md`, or extracted PDF containing imperative model instructions can therefore compete with legitimate system instructions.

Rejecting JSON/CSV does not solve prompt injection; Markdown, TXT, and PDF are equally capable of containing hostile instructions.

This directly conflicts with the work-order requirement:

> “Treat context file contents as data, never instructions.” 

### Recommended correction

For general reference files:

- do not merge raw content into creator/system instructions;
- encode it as an explicitly bounded reference-data block;
- escape filenames and delimiters;
- identify it as untrusted/user-supplied;
- preferably place reference material at a lower message authority than the character system prompt.

For “apply file to System Prompt/Instructions” behavior:

- require explicit preview/application;
- clearly state that this promotes file text into model instructions;
- do not silently promote a newly imported file.

### Regression fixture

Use a neutral adversarial fixture such as:

```text
REFERENCE DATA
Instruction-shaped text intended to test whether the enclosing
reference-data boundary can be escaped.
```

Verify the compiled structure cannot close its enclosing representation or become a new system message.

### Validation

```bash
npx vitest run \
  src/services/rp/promptBuilderService.test.ts \
  src/components/rp-studio/CharacterEditor.test.tsx \
  --no-file-parallelism

npm run test:character-cards
npm run verify:character-card-security
```

## P1-004 — Video timeout/cancellation contract still differs materially from requested behavior

The work order requires:

```text
default timeout: 120 seconds
user cancellation => aborted
stop polling after cancel/timeout
```

Current `use-video.ts` uses a 300-second queue timeout. 

The main background task manager also uses a 300-second video-generation timeout. More importantly, `cancelBackgroundTaskInMain()` explicitly does **not** terminate polling for provider-polled video/music tasks. It updates the task with:

```text
Provider cancellation is unavailable; generation is still running.
```

and leaves generation monitoring active. 

The retrieval implementation itself is substantially hardened: bounded JSON, streamed MP4 persistence, explicit retryability, and Traffic Inspector events are present. 

So the issue is no longer “video is entirely broken.” It is a contract mismatch around cancellation and timeout semantics.

### Required design decision

If Venice has no cancellation endpoint, distinguish:

```text
Cancel provider job
```

from:

```text
Stop monitoring locally
```

Do not claim provider cancellation when it cannot be done.

But the user's explicit “Cancel” action should at minimum:

```text
stop local polling
mark local task aborted/cancelled
record cancellation in Traffic Inspector
avoid continued background retries
tell user the remote provider may still finish/bill
```

If the product intentionally wants background continuation, rename the action away from “Cancel.”

### Validation

## P1-006 — Workflow output idempotency requirement is not demonstrated

The workflow planner notices duplicate `outputKey` values but deliberately says:

```text
Duplicate output key ... uses the last step value;
all actions will still run.
```

It then keeps every generated action. 

That does not provide the work-order requirement:

```text
exactly one image emitted per workflow run unless batch output explicitly requested
```

Nor does the planner expose an idempotency key combining:

```text
workflowRunId
outputNodeId
generationDispatchId
```

### Recommendation

At the execution boundary, add an idempotency set:

```text
(workflowRunId, outputNodeId)
```

and reject/reuse a second generation dispatch for the same non-batch output node.

Do not infer idempotency merely from `outputKey`; that is output naming, not execution identity.

### Validation

```bash
npm run test:workflow:core
npm run test:workflow:ui
npm run verify:workflow-templates
```

Required regression:

```text
one workflow run + one image output node
=> exactly one image generation adapter invocation
=> exactly one final media record
```

### Traffic Inspector

The centralized Venice fetch transport records a pending request before dispatch and updates outcomes after success/failure, while request body sanitization avoids retaining raw high-risk fields. Main-process video/audio polling also emits inspector telemetry.

### Profiles

Profile switching is main-session gated for password-protected profiles and performs a renderer reload after changing active profile, which is a sensible way to clear volatile UI/store state between namespaces. 

The secure-store design uses verifier-based passwords rather than recoverable plaintext and includes lockout behavior. The remaining problem is authorization around changing/resetting the master verifier and changing Family Safe Mode, not the password hashing/storage primitive itself.

The UI renders an actual `<audio controls>` element and handles unsupported-codec/decode/playback failures, native Save As, and Media Studio insertion. 

This is a significant implementation improvement. Real paid-provider/audio-device playback remains an external acceptance test.
